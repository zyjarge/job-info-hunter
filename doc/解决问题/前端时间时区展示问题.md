# FastAPI + Next.js 项目中的时区处理方案

## 问题描述

在前后端分离的项目中，后端 API（FastAPI）返回的时间是 UTC 时间，而前端（Next.js）需要显示本地时间（北京时间，UTC+8）。具体表现为：

- 数据库中存储的是 UTC 时间
- API 返回的时间没有正确转换时区  
- 前端显示的时间比实际时间少 8 小时

## 解决方案

### 1. 后端处理（FastAPI + Pydantic）

在 Pydantic 模型中配置时间序列化：

关键点说明：
- 使用 pytz 库处理时区转换
- `dt.replace(tzinfo=pytz.UTC)` 明确指定源时间为 UTC
- `astimezone(pytz.timezone("Asia/Shanghai"))` 将 UTC 时间转换为北京时间
- `isoformat()` 将时间转换为 ISO 格式的字符串

### 2. 前端处理（Next.js + TypeScript）

- 定义正确的接口类型
- 实现时间格式化函数

关键点说明：
- 使用 `Intl.DateTimeFormat` 进行标准的日期格式化
- 设置 `timeZone: "Asia/Shanghai"` 确保使用北京时间
- 设置 `hour12: false` 使用 24 小时制
- 添加错误处理，确保在数据异常时返回友好的提示

## 调试步骤

### 检查后端返回的时间格式：
- 确认数据库中存储的时间是 UTC 时间
- 检查 Pydantic 模型的时间字段定义
- 确保正确配置了 json_encoders

### 检查前端时间处理：
- 确认接口类型定义正确
- 检查时间格式化函数的实现
- 验证时区设置是否正确

### 测试验证：
- 重启后端服务使配置生效
- 刷新前端页面检查显示效果
- 对比显示时间与实际时间是否一致

## 注意事项

### 后端依赖：
- 需要安装 pytz 库：`pip install pytz`
- 确保 PostgreSQL 数据库正确处理时间类型

### 前端注意点：
- 使用 `Intl.DateTimeFormat` 而不是 `toLocaleString`，前者提供更好的国际化支持
- 始终处理空值和异常情况
- 考虑到不同时区的用户需求

### 通用建议：
- 数据库始终使用 UTC 时间存储
- 在 API 层进行时区转换
- 前端负责最终的格式化显示

这个方案可以确保在前后端分离的项目中正确处理时区问题，为用户显示正确的本地时间。
